# 实际项目评审

1. 选一条可追踪的用户或交付路径，从真实入口找到业务规则、写入方、配置来源、工作流和运行结果。确认同名旧目录、历史配置、测试替身和实际消费者的关系。
2. 记录源码 SHA、构建或发布回执、GitOps 期望版本和实际运行证据。每项结论只覆盖已观察的层级。用公共健康和版本接口可以证明该端点响应及自报版本。服务权限、数据库写入与可恢复性依赖各自的证据。
3. 运行现有入口的最小相关检查。对失败先定位断言、工具链、权限或实际行为。必要时在隔离 fixture 中验证重复、回滚、渲染或拒绝。必需测试缺失、跳过或环境受限时记录具体空白。
4. 给出有具体影响的差距及最小修正点。实际运行已满足契约时，可以保留具体函数、现有框架和模块。模式只用于解决已识别的变化点。评审范围外的风格、框架迁移及全仓重构无需列为整改。

- 源码与行为验证使用相应[开发规范](../../../README.md#开发规范)。
- 构建、发布门禁及跨仓回执按[CI/CD 工程规范](../../../engineering-standards/ci-cd-workflow-spec/SKILL.md)核对。
- 运行验收与回退按[服务目录和 Runbook](../../../operations-management/service-catalog-and-runbook-standard/SKILL.md)核对。
