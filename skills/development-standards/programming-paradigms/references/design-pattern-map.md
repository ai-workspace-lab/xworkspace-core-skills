# 经典设计模式选择表

先定位需要处理的变化点或一致性问题。表中的信号和代价用于决定是否引入模式。命名是沟通手段，代码可以使用函数、结构体、模块和现有框架原语实现。

| 模式 | 适用信号 | 当前技术栈中的落点 | 选型边界或验证 |
| --- | --- | --- | --- |
| Strategy 策略 | 同一用例需要按确定规则选择多个算法 | Go 函数或小接口，TS 函数映射，Python callable | 只有一种行为时直接调用。验证每个策略及选择规则。 |
| Adapter 适配器 | 外部接口、协议或数据形状与内部契约不同 | Next.js 上游 API 客户端，Go Provider 客户端，Python CLI 包装 | 明确格式、错误与取消语义的转换。 |
| Facade 外观 | 多个调用方需要相同的高层用例，内部涉及多个能力 | Gin 服务入口，Next.js 服务端功能模块 | 以业务动词命名，保留可定位的失败原因。 |
| Factory 工厂 | 对象构造确有多种配置或依赖组合 | Go 启动入口按配置选择实现，Python 创建 CLI 客户端 | 简单初始化用构造函数。配置无效时明确失败。 |
| Builder 构建器 | 对象分步组装，存在组合约束或可选参数交叉 | Python 复杂配置生成，Go 请求组装 | 普通参数对象可直接传入。验证缺项和不合法组合。 |
| Decorator 装饰器 | 多个调用点需要一致的日志、计时等横切处理 | Gin middleware，Go HTTP transport，Python decorator | 核对执行顺序、错误传播及身份边界。 |
| Chain of Responsibility 责任链 | 处理步骤按顺序检查且可终止请求 | Gin 鉴权 middleware，CLI 输入校验链 | 处理顺序显式。验证拒绝时后续步骤停止。 |
| Template Method 模板方法 | 总体顺序固定，少数步骤有明确变化点 | 可复用 workflow 或 Go/Python 函数接收步骤函数 | 调用方只注入允许变化的步骤，测试公共顺序。 |
| Command 命令 | 同一种操作由 HTTP、CLI 或任务入口触发，或需要排队 | Gin 和 CLI 共用业务用例，Python 子命令 | 明确每个入口的授权、幂等范围和结果。 |
| State 状态 | 允许的动作由当前状态决定，且转换需受控 | 订阅、工单、交付阶段，Go 显式状态转换配合 PostgreSQL 条件更新 | 简单状态用枚举和函数。验证非法转换、重入与并发。 |
| Observer 观察者 | 一个变化需要通知多个相互独立的接收者 | UI 订阅、进程内事件、异步消费者 | 明确同步性、顺序、失败传播和订阅清理。跨进程需要独立交付语义。 |
| Composite 组合 | 树形对象的叶节点与分组需要相同的递归处理 | React 树形菜单、Python 分组配置校验 | 平面列表用直接遍历。验证空分组、嵌套及终止条件。 |
| Proxy 代理 | 需要透明转发并集中实施访问控制、超时或缓存 | Next.js BFF 转发、Go HTTP 客户端代理 | 保持协议契约，明确凭据、缓存身份与失败传播。 |
| Iterator 迭代器 | 数据量大或分批获取，调用方需要逐条处理 | Python 生成器、Go 逐行读取、TS 异步迭代 | 小集合直接迭代。检查提前退出、资源释放和分页边界。 |
| Repository 仓储 | 同一业务数据访问契约被多个用例依赖，或查询细节需要隔离 | Go 的现有 store 或 repository，具体实现用 pgx/GORM | 避免按表生成通用 CRUD 层。验证真实 PostgreSQL 查询。 |
| Unit of Work 工作单元 | 一个用例中的多步写入必须共同成功 | Go 用例内显式 PostgreSQL 事务 | 共享同一事务句柄。验证提交、回滚和重复调用。 |
| Transactional Outbox 事务性发件箱 | 数据提交后必须可靠地产生跨系统事件 | PostgreSQL 同事务写业务记录和 outbox，worker 投递 | 接收方按事件标识幂等，处理重投、积压和观测。同步流程能满足时保持直接调用。 |
| Ports and Adapters 端口与适配器 | 业务规则需要隔离外部依赖，或同一用例有多个协议入口 | Gin、CLI 和数据库适配同一个 Go 用例 | 先确定真实依赖边界，再引入端口，避免为每个包增加接口。 |

**选择示例**

- Portal、Gin 和 PostgreSQL 共同实现订阅时，资格规则由 Gin 用例维护，Portal 负责交互和结果呈现。数据库通过约束保护可表达的持久化不变量。多步原子写入采用事务，需要可靠发送外部事件时再考虑 Outbox。
- 多个 GitHub Actions 作业共享固定的交付顺序时，先检查 reusable workflow。单作业内共享一组步骤时检查 composite action。多种入口复用同一渲染逻辑时，放进由其所属仓维护的 Python/Shell CLI。
- HCL 模块和 Playbook Role 用声明、参数和资源引用组合。只有 Provider 差异或实际可变策略需要独立适配时才增加一层。
