# 编程范式与设计模式选择

从实际入口追踪现有实现、调用方、状态写入和失败路径。先用现有结构与具体函数表达需求。出现真实的复用、替换或一致性问题时，按[设计模式选择表](references/design-pattern-map.md)匹配场景，并用受影响的调用路径验证。

## 项目抽样评审

按[实际项目评审](references/project-review.md)选择一条用户或交付链路。结论附版本、行为证据和最小修正点。具体范式和模式按已观察到的变化点选择。

## 编程范式

| 场景 | 首选范式 | 当前技术栈中的落点 |
| --- | --- | --- |
| 按顺序执行且有明确副作用 | 过程式 | Shell 调用已有 CLI，Python 编排多个操作，Go 用例显式组织事务。 |
| 数据校验、映射与计算 | 函数式组合 | TS/Python 数据转换和 Go 业务计算使用小函数，输入输出明确，副作用在调用边界。 |
| 由状态决定界面或目标配置 | 声明式 | React 根据状态渲染，HCL 描述资源，Ansible 模块表达主机状态，GitHub Actions 声明作业依赖。 |
| 保护对象的不变量和生命周期 | 封装与组合 | Go 结构体、函数和小接口，TS/Python 模块或对象封装真实状态。继承只用于已有明确的替换契约。 |
| 多步数据变更必须一致 | 事务式 | PostgreSQL 约束和原子写入，Gin 用例持有事务范围。 |
| 调用方可延迟获取结果，任务需要独立重试或处理积压 | 事件驱动 | Go/Python worker 消费事件，定义幂等、重试、顺序及失败观测。 |

## 按业务能力组织

- 优先沿用当前模块结构。按业务语义归置代码，入口适配器调用用例，用例依赖清晰的数据或外部能力。只有需要独立部署、扩缩容、故障隔离或数据所有权时才评估拆服务。
- 同一业务规则、配置和数据各有权威来源。比较语义、权限、生命周期和失败行为，确认一致再抽取公共实现。字段或代码长得相似但业务含义不同的模块可以各自演进。
- 采用模式时记录触发场景、对应契约和可验证结果。抽象层应承载变化、隔离依赖或保护一致性。只有结构变动的重构需要保留已有行为，并通过正常调用入口验证。
- 对长期运行的 Web/API/worker，按[云原生十二要素](references/twelve-factor.md)审查。静态站点、短时 CLI 和基础设施声明只选用与自身运行模型相关的要素。

## 命名、可读性与轻量扩展

符号命名、避免晦涩语法、以及在现有边界内做轻量扩展，按[命名与可读性清单](references/naming-and-clarity.md)检查。先跟随所在目录已有写法；不要为统一风格而批量改名，也不要提前引入额外抽象层。
