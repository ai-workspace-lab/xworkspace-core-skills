# 单主题技术文章系列（循环模板）

## 铁律（每篇都必须）
- 爆款标题：具体、有冲突或数字，但不夸大、不超出事实。
- 只讲 1 个背景、1 个痛点、1 个方案；多出来的话题拆成另一篇。
- 结尾一张「架构视角决策表」：功能 / 特性 / 成本 / 客观事实依据 / 适用场景；每格有来源，未实测写【待实测】。
- 3–5 张纯技术架构图（可做 GIF，箭头流动）：图内不放日期、合作/授权说明、图说、待实测标记、署名。
- 微信：严格 ≤1500 字，3–5 段，InfoQ 风格（客观、密度高、少形容词）。
- XHS：严格 600–800 字（非空格字符），种草风格，口语、分页 P1…Pn。
- 不编数字；不写秘钥、内网地址、凭据路径；用脚本数字数，超限就删。

## 循环模板（按序轮换，相邻两篇不用同一个）
1. **故障复盘型**：一次失败现场 → 为什么现有工具看不见 → 方案 → 复盘清单 → 决策表。
2. **对比选型型**：A vs B 的一个具体场景 → 各自边界 → 结论 → 决策表。
3. **误区纠偏型**：「你以为…其实…」开头 → 事实依据 → 正确做法 → 决策表。
4. **动手实操型**：目标 → 3–5 步 → 每步的验证点 → 决策表。
5. **成本账本型**：一笔账的来源 → 隐性成本 → 省钱/省人力的办法 → 决策表。
6. **问答拆解型**：3–5 个读者真会问的问题依次回答 → 决策表。

## 步骤
1. 盘点素材，列出「背景–痛点–方案」三元组，每组一篇。
2. 按系统先后排序（为什么 → 边界 → 怎么做 → 怎么验证 → 怎么回退/演进），给每篇指派一个模板，循环使用。
3. 每篇文末加一句「上一篇 / 下一篇」串联，形成闭环。
4. 画图（Graphviz 等源文件可复用），必要时生成箭头流动 GIF。
5. 写微信版和 XHS 版，脚本核字数。
6. 输出 index.md：序号、标题、模板、背景、痛点、方案、字数、图清单。
7. 交用户审阅；发布、提交仓库、上传都等用户明确要求。
